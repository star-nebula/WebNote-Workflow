## 最近 OpenClaw 这么火，你知道它的原理吗？
- 要点1：OpenClaw 定位为"多渠道 AI 网关"，自身不做推理，只做调度和执行，把 LLM 的推理能力翻译为对操作系统、软件 API、硬件设备的实际控制权（回答重点第1段，"OpenClaw 本质上是一个开源的多渠道 AI 网关"）
- 要点2：核心运行时机制是 Agentic Loop（ReAct 范式），六步循环：Load → Call → Parse → Execute → Append → Loop，循环持续直到 LLM 输出最终文本（回答重点第6-9段）
- 要点3：Gateway 是区别于其他 AI 编程工具的核心独有模块，以守护进程方式 7×24 运行，承担六件事：常驻在线、多平台接入、会话隔离、排队控制、心跳巡检+Cron 定时调度、记忆刷盘（扩展知识-Gateway 网关第1段，"Gateway 才是 OpenClaw 区别于其他 AI 编程工具的核心独有模块"）
- 要点4：技能系统（Skills）采用渐进式披露，元数据层始终轻量加载，完整指令仅在语义匹配命中时加载，解决多工具下上下文爆炸问题（扩展知识-技能系统第1-4段）
- 要点5：记忆系统采用混合搜索（BM25 + 向量余弦相似度），支持时间衰减和 MMR 多样性重排，数据全部存在本地（扩展知识-记忆系统第1-6段）
- 为什么值得保留：OpenClaw 核心原理的完整综述，涵盖架构、运行时、Gateway、技能、记忆五大模块，是后续所有专题的总纲
- 修订建议：值得深读

## （OpenClaw前置知识）什么是 AI Agent？它和直接调用大模型 API 做一次问答有什么本质区别？
- 要点1：AI Agent 与单次 API 调用的本质区别有三点：工具调用能力（能操作外部世界）、记忆和上下文（有状态）、自主决策循环（自己规划步骤迭代推进）（回答重点第2-4段）
- 要点2：OpenClaw 内置了文件读写、Shell 执行、浏览器控制、Web 搜索、记忆检索等 25 个核心工具（扩展知识-Agent 的核心架构第2段，"OpenClaw 内置了...25 个核心工具"）
- 要点3：Agent 一次复杂任务跑下来，光 API 费用可能就 2-5 美元，10 轮循环可能吃掉 3-15 万 token（扩展知识-Agent 的常见坑点第1段）
- 要点4：RAG 本质上可以看作 Agent 的一个工具，解决"让模型获取外部知识"的问题，Agent 解决"让模型执行复杂任务"的问题（面试官追问第2问）
- 要点5：Agent 的 token 优化核心思路：上下文压缩、工具结果精简、分层调度（小模型做简单决策/大模型做复杂推理）、缓存重复工具调用结果（面试官追问第4问）
- 为什么值得保留：清晰定义了 Agent 与简单 API 调用的边界，包含 Agent 核心架构三模块（大脑/手脚/笔记本）的经典框架

## （OpenClaw前置知识）请解释 Tool Calling（工具调用）的完整链路
- 要点1：Tool Calling 核心链路四步：定义工具（JSON Schema）→ LLM 决策调用（返回 tool_use）→ 系统执行（解析并调用本地函数）→ 结果回传（tool_result 追加到对话历史）（回答重点第1-7段）
- 要点2：从 Function Calling 到 Tool Calling 的关键演进：2023 年 11 月起支持 parallel tool calls，LLM 一次可返回多个 tool_use 并行执行（扩展知识第1段）
- 要点3：工具数量超过 15-20 个时 LLM 选择准确率会明显下降，需要分场景加载或意图路由（面试官追问第4问）
- 要点4：不同 Provider 对 Schema 支持有差异：Gemini 不支持 patternProperties/additionalProperties，xAI 不支持 minLength/maxLength，OpenAI 要求顶层必须是 type: "object"（扩展知识第3段）
- 要点5：生产环境安全必备三层：工具白名单、服务端参数校验、敏感操作加人工确认（扩展知识-安全和权限控制第1-2段）
- 为什么值得保留：Tool Calling 完整链路的标准答案，含 parallel tool calls 演进、跨 Provider 差异、安全实践
- 修订建议：值得深读

## （OpenClaw前置知识）System Prompt 在 Agent 系统中承载了哪些职责？
- 要点1：System Prompt 承载五大职责：角色定义和行为准则、工具使用规范和约束、输出格式要求、安全与权限控制、上下文信息补充（回答重点第3-7段）
- 要点2：处理 System Prompt 越来越长的核心策略三个字：拆、选、扔——模块化拆分、按需加载、大体积低频知识外置（回答重点第9段）
- 要点3：模块顺序确实影响模型行为，模型对 System Prompt 开头和结尾关注度更高，中间部分易被"稀释"。OpenClaw 的拼接顺序：Identity → Tooling → Safety 在最前面，Skills/Memory 在中间，Runtime 信息在最后（面试官追问第2问）
- 要点4：判断知识放 prompt 还是放外部：超过 500 token 且使用频率低于 30% 的信息放外部更经济（面试官追问第3问）
- 要点5：安全不能只靠 System Prompt，必须分层防御：System Prompt 写红线（第一道）+ 代码级硬控制（第二道），如 before_tool_call 钩子拦截、exec 工具审批机制（面试官追问第1问）
- 为什么值得保留：System Prompt 设计的完整方法论，含模块化组装、插件钩子、prompt cache 优化、分层安全
- 修订建议：值得深读

## （OpenClaw前置知识）什么是 Agent 的 Context Window？
- 要点1：Agent 一次请求里塞的内容：System Prompt 2000-5000 token，工具定义（20 个工具）4000-10000 token，对话历史最易膨胀（单条 tool result 可达 3000-8000 token，10 轮后轻松超 50K token）（扩展知识第1-5段）
- 要点2：OpenClaw 设了两道防线：硬下限 16,000 token（低于直接拒绝运行），软告警 32,000 token（低于警告用户）（扩展知识-OpenClaw 的 Context Window 管理机制第2-3段）
- 要点3：中文文本 token 开销比等长英文高 2-3 倍，不同模型 tokenizer 计算结果可能差 10%-20%（扩展知识-token 计算的坑第1-3段）
- 要点4：OpenClaw 用各模型对应 tokenizer 做精确计算，同时留出 10% 安全余量（扩展知识-token 计算的坑第4段）
- 要点5：主流 Context 管理策略：滑动窗口（简单但丢信息）、摘要压缩（效果好但有延迟成本）、分层存储（按优先级保留）、外部检索（存向量库按需检索），生产中混合使用（扩展知识-主流的 Context 管理策略）
- 为什么值得保留：Context Window 约束的完整量化分析，含 token 构成、中英文差异、OpenClaw 防线设计
- 修订建议：值得深读

## （OpenClaw前置知识）解释「短期记忆」和「长期记忆」在 Agent 系统中的区别
- 要点1：短期记忆精度高但容量有限（受 context window 约束），长期记忆容量几乎无限但检索有损（召回内容不一定完全匹配）（回答重点第3-5段）
- 要点2：短期记忆 compaction 三种策略：滑动窗口（保留最近 N 轮）、摘要压缩（LLM 生成摘要替换原文）、选择性保留（按重要性打分），生产环境组合使用（扩展知识-短期记忆的管理策略）
- 要点3：长期记忆需要混合检索（向量 + 全文）的原因：纯向量搜索语义模糊，纯全文搜索无法捕捉同义表达，两者互补（扩展知识-长期记忆的存储和检索第3-5段）
- 要点4：Memory Flush 是关键设计模式：对话接近压缩阈值时，先让 LLM 提取关键信息写到持久化存储，再执行压缩（扩展知识-短期记忆到长期记忆的自动转化第1段）
- 要点5：长期记忆写入太频繁会导致噪音，需要去重和过期清理（如 30 天未命中自动降权）；更换 embedding 模型后旧向量全部作废，需要同时存原文（扩展知识-常见的坑第1-2段）
- 为什么值得保留：短期/长期记忆的完整对比，含 compaction 策略、混合检索原理、Memory Flush 机制、常见坑
- 修订建议：值得深读

## OpenClaw 的核心组件有哪些？请描述它们之间的关系
- 要点1：五层核心组件：Channel Plugins（协议转换）→ Gateway（中枢鉴权限流）→ Routing（Agent 匹配）→ Agent Runner（执行引擎）→ Context Engine（上下文管理）（回答重点第1-5段）
- 要点2：分层的原因：Channel 层屏蔽多平台协议差异，Gateway 收敛横切关注点，Routing 支持多 Agent 调度，Agent Runner 封装执行复杂度，Context Engine 抽象上下文管理（扩展知识-为什么要分这么多层）
- 要点3：Context Engine 接口定义在 `src/context-engine/types.ts`，核心三件事：ingest（摄入）、assemble（组装 Prompt）、compact（压缩历史）。默认 legacy 实现中 ingest 是 no-op，assemble 直接透传，compact 委托给 compaction 模块（扩展知识-源码层面的落点第5段、面试官追问第2问）
- 要点4：Agent Runner 防死循环靠多层保护：执行超时、tool-loop-detection.ts 四种检测策略（generic_repeat/ping_pong/known_poll_no_progress/global_circuit_breaker）、context overflow 自动降级（面试官追问第3问）
- 要点5：Gateway 幂等去重通过提取消息唯一标识（如 Telegram message_id），在本地缓存里做去重判断（面试官追问第4问）
- 为什么值得保留：五层组件架构的清晰拆解，含源码路径、接口定义、防死循环机制

## 在 OpenClaw 中，一条用户消息从进入系统到收到回复，完整链路是怎样的？
- 要点1：完整链路分入站、路由、执行、出站四个阶段共 8 步：渠道适配器接收 → 转换 MsgContext → dispatchInboundMessage 补全 → resolveAgentRoute 路由匹配 → 斜杠命令检查 → runReplyAgent 启动 → LLM+工具循环 → ReplyDispatcher 投递（回答重点第1-7段）
- 要点2：两层排队：enqueueSession（session 级，保证同一 session 串行）和 enqueueGlobal（全局，控制总并发数，防止打爆 LLM API rate limit）（扩展知识-排队机制）
- 要点3：Fallback 是 model-level 的，只切换 provider 和 model，系统提示词、工具列表等 Agent 配置全部保持不变（扩展知识-Fallback 机制、面试官追问第2问）
- 要点4：idempotencyKey 不是根据消息内容生成，而是用渠道推送的消息 ID（如 Telegram message_id、Discord snowflake），两个用户发相同内容不会误判（面试官追问第3问）
- 要点5：Telegram 不支持原生流式，OpenClaw 用两种模拟策略：优先使用 sendMessageDraft 草稿消息接口，不可用时 fallback 到先发空消息再循环 editMessageText 逐步追加（扩展知识-流式输出第3段）
- 为什么值得保留：完整消息链路的端到端描述，含排队、幂等、Fallback、流式适配、Hook 插入点
- 修订建议：值得深读

## OpenClaw 的 Agent Runner 是如何工作的？一次 Agent 运行经历了哪些阶段？
- 要点1：一次完整 Agent 运行六阶段：排队 → 准备 → 插件+Hook → 模型解析+鉴权 → 尝试执行（核心循环）→ 溢出降级（回答重点第1-6段）
- 要点2：容错分两层：Auth Profile 轮转（同 Provider 换 Key 重试）和模型级 Fallback（换备用模型），重试上限 32-160 次（根据 profile 数量动态计算），服务过载加指数退避（扩展知识-attempt + fallback 容错机制）
- 要点3：工具调用经过双层包装：Hook 拦截层（参数校验、权限检查、循环检测）+ 取消机制层（合并 AbortSignal，支持用户中断）（扩展知识-工具调用的双层包装）
- 要点4：Context 溢出三级降级：先 compaction 压缩历史 → 再截断超大 tool result（单条最多占上下文窗口 30%，动态判断尾部重要性）→ 最后报错降级建议开新会话（扩展知识-Context 溢出的三级降级）
- 要点5：历史消息以统一中间格式存储在 session 文件中，fallback 切换模型时自动做格式适配（如 Gemini/Anthropic 的 turn 交替规则差异），对历史消息透明（面试官追问第2问）
- 为什么值得保留：Agent Runner 全流程拆解，含容错、工具包装、溢出降级、Provider 流式适配
- 修订建议：值得深读

## LLM 的 Context Window 有上限，长对话时如何保证 Agent 仍然能正常工作？
- 要点1：OpenClaw 的四层分层防御：Context Pruning（修剪）→ Tool Result Context Guard（兜底）→ Memory Flush（记忆刷盘）→ Compaction（压缩），从轻到重依次上手段（回答重点第1-5段）
- 要点2：Context Pruning 两级阈值：softTrimRatio（默认 0.3，触发 head+tail 裁剪，保留前/后各 1500 字符）和 hardClearRatio（默认 0.5，触发 placeholder 替换），保护规则包括最近 3 条 assistant 消息和 System Prompt 不可删（扩展知识-Context Pruning 的实现细节）
- 要点3：Tool Result 截断时通过 hasImportantTail() 检测尾部是否含 error/exception/exit code/traceback 等关键词，有则优先保留尾部——因为错误信息通常比正常输出更有价值（扩展知识-Tool Result 截断的巧妙设计）
- 要点4：Tool Result Context Guard 计算 context budget = context window × 4 chars/token × 0.75 headroom，从最早 tool result 开始逐个替换为占位符（扩展知识-Tool Result Context Guard 兜底机制）
- 要点5：Compaction 有 identifier preservation 指令，要求保留 UUID、hash、URL、文件名等不可重建的标识符（扩展知识-Compaction 摘要的质量问题第3段）
- 为什么值得保留：Context 管理的四层防御体系完整拆解，含具体阈值参数和保护规则
- 修订建议：值得深读

## Agent 调用工具可能返回超大结果（比如代码搜索返回 50KB），这会带来什么问题？
- 要点1：50KB 文本按 1 token ≈ 4 字符估算约 12000+ token，对 128K context 模型吃掉近 10%（回答重点第2段）
- 要点2：OpenClaw 两层防护：单条截断（硬上限 400K 字符，且不超过 context window 的 30%）+ 全局预算守卫（所有消息总字符超 context window × 4 × 0.75 时，从最早 tool result 开始替换为占位符）（回答重点第4-5段）
- 要点3：head+tail 截断仅在 hasImportantTail() 检测到尾部含 error/exception/failed/traceback 等关键词时启用：tail 占 budget 30%（上限 4000 字符），head 占剩余（至少 2000 字符），否则默认只保留开头（回答重点第3段、面试官追问第2问）
- 要点4：对 tool result 使用 TOOL_RESULT_CHARS_PER_TOKEN_ESTIMATE = 2（而非通用 4），因为代码和结构化文本 token 密度更高（扩展知识-字符预算的计算第3段）
- 要点5：截断后附加提示语告知模型内容被截断，建议使用 offset/limit 参数重新获取，帮助模型做二次精确查询（面试官追问第1问）
- 为什么值得保留：超大 tool result 处理的完整工程方案，含具体截断参数、预算计算公式、动态策略
- 修订建议：值得深读

## 当对话历史实在太长、裁剪也不够用时，还有什么办法？什么是 Compaction？
- 要点1：Compaction 四步流程：分块（Chunking）→ 逐块摘要（Per-chunk Summarization）→ 合并摘要（Merge Summaries）→ 摘要增强（Summary Augmentation），核心是"信息保全式压缩"而非"信息舍弃式截断"（回答重点第1-5段）
- 要点2：摘要必须保留 5 个结构化章节：Decisions（决策）、Open TODOs（待办）、Constraints/Rules（约束）、Pending user asks（未回应的请求）、Exact identifiers（精确标识符）（扩展知识-摘要质量检查第1段）
- 要点3：strict 标识符保留策略要求精确保留 UUID、hash、API key、URL、文件名等不可重构标识符，丢失后无法推导（扩展知识-标识符保留策略）
- 要点4：Compaction 触发时机按 token 数而非固定轮次，因为每轮对话长度差异极大（面试官追问第3问）
- 要点5：单次 Compaction 消耗约几千 token，但能将数万 token 历史压缩到几千 token，100 轮对话不压缩会烧掉几十万 token（面试官追问第1问）
- 为什么值得保留：Compaction 的完整工程实现，含分块策略、摘要质量检查、标识符保留、token 经济性分析
- 修订建议：值得深读

## OpenClaw 把 Context 管理抽象成了可插拔的 Context Engine，为什么要做这层抽象？
- 要点1：ContextEngine 接口覆盖完整生命周期：bootstrap（初始化）、ingest/ingestBatch（存消息）、assemble（挑消息）、compact（压消息）、afterTurn（轮后处理）、子 Agent 管理、dispose（销毁）（回答重点第4段）
- 要点2：至少能支撑五种策略方向：legacy 线性压缩、基于检索的 RAG、分层存储（冷热分离）、任务感知、自定义压缩（树状摘要等）（回答重点第6段）
- 要点3：ownsCompaction: true 标记控制日常由谁管压缩：设了则禁用 Pi runtime 内置 auto-compaction，由引擎自主管理；但无论设没设，Runner 在上下文溢出时都会强制调用 compact() 兜底（面试官追问第3问）
- 要点4：legacy 引擎的 ingest 是 no-op（消息持久化由 SessionManager 负责），换成 RAG 引擎后 ingest 需接管向量化和入库（面试官追问第1问）
- 要点5：不同引擎面对 token 预算紧张时的降级策略差异：legacy 从最早消息暴力砍，RAG 按相关性少捞几条（质量衰减平滑），分层存储优先砍冷数据，任务感知按任务权重动态决定（面试官追问第2问）
- 为什么值得保留：策略模式在 Agent 上下文管理中的经典应用，含接口设计、五种策略方向、降级策略对比
- 修订建议：值得深读

## 如果一个 Agent 系统要同时接入 Telegram、飞书、钉钉等渠道，你会怎么设计抽象层？
- 要点1：核心设计是适配器模式+三层架构：统一消息模型（核心字段+扩展字段）→ 适配器协议（按能力拆成独立小接口，渠道按需组合）→ 能力声明（capabilities 自动降级）（回答重点第1-4段）
- 要点2：OpenClaw 的 ChannelPlugin 接口拆成多个维度：id/meta 标识、capabilities 能力声明、outbound 发消息、gateway 收消息、status 探活、groups 群组、mentions @提及、agentTools 渠道特有工具、config 配置解析（扩展知识-OpenClaw 的 ChannelPlugin 设计）
- 要点3：ChannelDock 是轻量元数据层，Gateway 做路由和策略判断时只需加载元数据而非完整插件，是按需加载思想在插件架构上的体现（扩展知识-轻量元数据层的设计）
- 要点4：限流逻辑必须放在各自 adapter 内部，不能放统一层，因为各渠道限制维度不同（Telegram 按 bot 全局、Discord 按 channel、Slack 按 workspace）（面试官追问第3问）
- 要点5：跨渠道上下文打通需要一个跨渠道用户身份映射层，把不同渠道用户 ID 关联到同一内部标识，OpenClaw 目前选择按渠道隔离（面试官追问第4问）
- 为什么值得保留：多渠道接入的完整架构设计，含适配器模式、能力声明降级、ChannelDock 轻量元数据层
- 修订建议：值得深读

## 同一个系统里可能有多个 Agent，不同渠道用户群组的消息需要路由到不同的 Agent
- 要点1：核心设计是声明式规则+优先级匹配，从精确到模糊共 8 级：binding.peer → peer.parent → guild+roles → guild → team → account → channel → default（回答重点第1-2段）
- 要点2：路由结果不只是 agentId，还同步计算 sessionKey（会话隔离）、mainSessionKey（DM 折叠）、matchedBy（命中规则），路由和会话隔离联动完成（扩展知识-路由结果不只是 agentId）
- 要点3：8 级优先级匹配每级就是一次 Map.get 或简单字段比对，加起来几微秒，一条消息完整处理耗时 1-10 秒，路由开销可忽略（面试官追问第2问）
- 要点4：同一优先级配两条规则命中同一消息属于配置 bug，应在配置校验阶段拦截（面试官追问第1问）
- 要点5：要支持基于消息内容的路由，可在优先级链中插入 binding.content 级别，匹配逻辑用正则或关键词，高性能场景需 Aho-Corasick 多模式匹配（面试官追问第3问）
- 为什么值得保留：多 Agent 路由的声明式设计范式，含 8 级优先级、sessionKey 联动、性能分析、扩展方案
- 修订建议：值得深读

## 同一个用户在 Telegram 私聊和 Discord 群组里和 Agent 对话，应该共享会话还是隔离？
- 要点1：应该隔离。私聊和群聊的语境、隐私要求完全不同，群聊里其他人能看到 Agent 回复，混入私聊上下文等于隐私泄露（回答重点第1-2段）
- 要点2：Session Key 格式 `agent:{id}:channel:{type}:peer:{id}`，四个维度编码到一起，不同组合天然不同，无需额外隔离逻辑（回答重点第3段）
- 要点3：私聊隔离粒度通过 dmScope 配置 4 级：main（全私聊共享）、per-peer（同用户跨渠道共享）、per-channel-peer（默认，同渠道同用户共享）、per-account-channel-peer（最细，区分 bot 账号）（扩展知识-私聊场景的隔离粒度控制）
- 要点4：Thread 分配独立 session key（在基础 key 后拼 `:thread:{threadId}` 后缀），同一群组内不同 Thread 上下文完全隔离（扩展知识-群组和 Thread 的隔离第2段）
- 要点5：会话隔离只影响运行时上下文加载，不影响数据层面聚合；session key 已编码所有维度，分析系统按 peer 聚合即可拿到全渠道记录（面试官追问第3问）
- 为什么值得保留：会话隔离粒度的完整设计，含 Session Key 构造、4 级 dmScope、Thread 隔离、数据聚合解耦
- 修订建议：值得深读

## 同一个工具（比如「执行命令」）在不同场景下应该有不同的权限
- 要点1：OpenClaw 定义 7 层策略管道，漏斗式逐层收窄：tools.profile → tools.byProvider.profile → 全局 allow/deny → Provider 级 allow → Agent 级 allow → Agent-Provider 级 allow → Group 级 allow（回答重点第2段）
- 要点2：策略管道遵循单调递减原则：后续层只能在前一层结果集内进一步缩小，不能反向扩大。全局 deny 了就是 deny 了，Agent 级 allow 无法覆盖（面试官追问第1问）
- 要点3：deny 优先于 allow，实现逻辑是先用 allow 构建候选集，再用 deny 从中剔除（面试官追问第2问）
- 要点4：Owner-only 工具选择直接从工具列表移除而非调用时拒绝，原因是减少攻击面——LLM 压根不知道这个工具存在，无法通过 prompt injection 绕过（面试官追问第3问）
- 要点5：子 Agent 默认 deny spawn 操作，如需放开通过 tools.subagents.tools.allow 配合深度限制（如最大嵌套 3 层、并发子 Agent ≤5）（面试官追问第4问）
- 为什么值得保留：工具权限控制的纵深防御设计，含 7 层管道、单调递减原则、deny 优先、攻击面最小化
- 修订建议：值得深读

## 不同的 LLM Provider 对 Tool Schema 的支持不完全一致，你会怎么处理这种差异？
- 要点1：核心方案是 Schema 归一化：工具只用标准 JSON Schema 定义一次，normalizeToolParameters() 根据目标 Provider 自动清洗转换（回答重点第1-2段）
- 要点2：各 Provider 差异具体：Gemini 不支持 oneOf/anyOf/additionalProperties/patternProperties，xAI 不支持 minLength/maxLength，OpenAI 要求顶层必须是 type: "object"（回答重点第3段）
- 要点3：oneOf 展平策略：合并同名字段的 properties（如 enum 值合并），required 仅保留所有 variant 中都出现的字段，最大限度保留语义（扩展知识-源码解析第2段）
- 要点4：工具数与 Provider 数是乘法关系（30 工具 × 5 Provider = 150 份 Schema），"一次定义、按需转换"架构避免维护爆炸（扩展知识-为什么不让开发者自己适配）
- 要点5：Schema 约束本质是提示而非强制校验，清洗中移除了 minLength 等约束后，工具端仍需做二次参数校验兜底（面试官追问第1问）
- 为什么值得保留：跨 Provider Schema 适配的完整工程方案，含归一化架构、各 Provider 差异清单、展平策略
- 修订建议：值得深读

## Agent 系统中 Hook/中间件模式有什么用？OpenClaw 的 Hook 系统是怎么设计的？
- 要点1：Hook 分两层：内部 Hook（字符串事件名，如 `message:received`，覆盖 command/session/agent/gateway/message）和插件 Typed Hook（强类型命名，如 `before_model_resolve`、`before_prompt_build`、`llm_input`）（回答重点第3段）
- 要点2：Hook 分为两种执行模式：Void Hook 并行执行无返回值（用于观测记录），Modifying Hook 串行按优先级依次执行可返回并合并数据（用于修改数据流）（扩展知识-Hook 的两种执行模式）
- 要点3：priority 数字越大优先级越高，多个 Modifying Hook 按 priority 降序串行执行，形成管道式处理链（扩展知识-Hook 的注册和优先级）
- 要点4：与 LangChain Callback 的区别：LangChain 更偏向观察记录，OpenClaw 的 Hook 可直接修改数据流（如 before_model_resolve 换模型、llm_input 改写输入），拦截能力更强（扩展知识-和其他框架的 Hook 机制对比）
- 要点5：默认每个 Hook 执行 try-catch 包裹，单个报错只打日志继续执行。更优设计支持 Hook 注册时声明 critical: true/false，critical 报错中断请求（面试官追问第2问）
- 为什么值得保留：Hook 系统的完整设计，含双模式执行、优先级机制、与 AOP/LangChain Callback 的对比
- 修订建议：值得深读

## 什么场景下需要多 Agent 协作而不是单个 Agent 解决？OpenClaw 是怎么支持子 Agent（Subagent）的？
- 要点1：三种典型场景：任务天然可并行拆分、不同子任务需要异构模型/工具/权限配置、单 Agent context window 装不下所有信息（回答重点第1-3段）
- 要点2：子 Agent 三步模型：派活（sessions_spawn 创建独立 session）→ 干活（独立执行，有自己的工具集和模型）→ 交差（Announce 推模式自动回传结果，带幂等 key）（回答重点第4-6段）
- 要点3：子 Agent 两种运行模式：run 模式（执行完即销毁，适合一次性任务）和 session 模式（保持会话，支持后续继续发指令）（扩展知识-子 Agent 的两种运行模式）
- 要点4：并发控制靠 subagent lane（并发槽位，如容量 5 则最多 5 个并行）+ maxSpawnDepth（嵌套深度限制，默认 1）（面试官追问第3问）
- 要点5：子 Agent 与父 Agent 完全隔离，上下文通过创建时的 prompt 显式传入摘要而非原始数据，强制信息显式传递避免敏感信息泄露（面试官追问第1问）
- 为什么值得保留：多 Agent 协作的完整方案，含判断标准、spawn+announce 原语、运行模式、并发控制
- 修订建议：值得深读

## 多 Agent 之间如何通信和协调？OpenClaw 的 Gateway 在其中扮演什么角色？
- 要点1：两条通信路径：Announce 机制（子 Agent 完成自动推结果回父 Agent session）+ 斜杠命令交互（父 Agent 主动给子 Agent 发指令）（回答重点第1-2段）
- 要点2：Gateway 是中央调度器，所有 Agent 运行、spawn 分发、announce 路由都经它，通过两级排队（session 级+全局）保证同一 session 串行、总量可控（回答重点第3段、扩展知识-排队与并发控制）
- 要点3：子 Agent announce 消息携带稳定 idempotency key，Gateway 通过 dedupe map 去重，防止网络抖动导致父 Agent 重复收到结果（扩展知识-幂等性保证）
- 要点4：Gateway 维护的关键运行时状态：dedupe map（去重）、agentRunSeq（执行顺序追踪）、chatRunState（调度决策）（扩展知识-Runtime State 管理）
- 要点5：多个子 Agent 结果到达顺序不确定，父 Agent 不依赖网络顺序，而是按 announce 消息中的任务 ID 匹配处理，必要时结合 agentRunSeq 自行排序（面试官追问第3问）
- 为什么值得保留：多 Agent 通信协调的完整架构，含 Gateway 角色、Announce 机制、运行时状态、去重
- 修订建议：值得深读

## OpenClaw 采用插件架构，设计一个插件系统需要考虑哪些关键问题？
- 要点1：四个核心问题：注册与发现（jiti JIT 加载，扫描 extensions/ 目录）、隔离性（包结构隔离，peerDependencies 约束）、API 稳定性（统一 plugin-sdk 入口收敛暴露面）、扩展点粒度（每种能力独立注册入口）（回答重点第1-4段）
- 要点2：Plugin API 提供 7 种注册方法：registerTool、registerChannel、registerHook/on、registerProvider、registerHttpRoute、registerService、registerCommand（回答重点第4段表格）
- 要点3：PluginRegistry 是 IoC 控制反转的核心：插件主动向 Registry 注册，核心模块通过 Registry 查询，不硬编码依赖任何具体插件（扩展知识-PluginRegistry）
- 要点4：插件可通过 Registry 间接访问其他插件注册的能力（如 api.getRegisteredTools()），但禁止直接 import 其他插件源码，保证松耦合（面试官追问第4问）

## OpenClaw 的 Gateway 对 Agent 请求做了幂等性处理
- 要点1：幂等实现：idempotencyKey（UUID）+ Gateway 内存 dedupe Map，先查缓存有则直接返回，无则执行后存入。缓存有 TTL 和 DEDUPE_MAX 限制（回答重点第2段）
- 要点2：对已产生副作用的策略是"防止重复触发，不做回滚"，已执行的副作用保留，重点保证后续不再重复（回答重点第3段）
- 要点3：消息发送场景有三层防护：dedupe Map（历史上发过没）+ inflightMap（当前正在发没）+ transcriptHasIdempotencyKey()（对话历史中是否已存在该幂等键）（扩展知识-消息发送的双层防护）
- 要点4：缓解不可幂等工具副作用的三层策略：优先设计幂等工具（如写文件）、工具侧自行去重（发消息前查 message ID）、接受"至多一次"语义（宁可漏执行不重复）（扩展知识-处理已产生副作用的策略）
- 要点5：内存 dedupe 重启后丢失，单实例部署下重启窗口短风险可控；分布式多实例需换 Redis SETNX 或在入口加一致性哈希（面试官追问第1-2问）
- 为什么值得保留：Agent 幂等性的完整工程方案，含三层防护、副作用策略、分布式扩展
- 修订建议：值得深读

## 如果让你基于 OpenClaw 的设计理念从零搭建一个 Agent 框架，你会先做哪三个模块？
- 要点1：三个模块的优先级：Agent Runner（执行引擎）→ Context Engine（上下文管理）→ Gateway（请求网关），是最小可运行系统的核心（回答重点第1-3段）
- 要点2：Agent Runner 关键设计决策：模型抽象层（定义 LlmClient 接口，底层随便切换）、工具注册用声明式（注解或配置描述）、错误处理和超时从第一版就搭好（扩展知识-Agent Runner 的核心设计）
- 要点3：Context Engine 核心矛盾是 token 窗口有限但对话历史越来越长，OpenClaw 分层管理：最近几轮原文保留、更早历史 compaction 压缩成摘要、System Prompt 和工具描述单独管理不裁（扩展知识-Context Engine 的设计要点）
- 要点4：Gateway 承担六大类职责：消息渠道管理、会话管理与请求排队、幂等去重、定时任务（Cron）、子 Agent 协调、配置热更新与运维（扩展知识-Gateway 的职责全景）
- 要点5：LLM 返回不存在的工具名时，构造 tool_result 告知"工具不存在，请重新选择"，让 LLM 重新决策，加最大重试次数（如连续 3 次调错就终止）（面试官追问第1问）
- 为什么值得保留：从零搭建 Agent 框架的路线图，含三个模块的优先级论证、关键设计决策、Gateway 六大职责全景
